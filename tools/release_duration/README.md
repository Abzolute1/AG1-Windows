# P14 duration controller

This controller submits the six unchanged original long-horizon repair tasks to the actual native client. It does not implement a model loop, manufacture extra model turns, or extend a completed task with generic nudges. Each repetition introduces a fresh, committed source regression. The model must retrieve the current archived contract, repair only the allowed source file, and pass the unchanged external verifier. Original obsolete contracts remain in the history.

A real eight-hour or 24-hour monotonic interval is mandatory. The driver works continuously, with at most 120 seconds between verified activities, at most 30 minutes per activity, and at least two completed tasks per requested hour. Mandatory admission, recovery and verification are recorded separately from model work. The clock cannot be satisfied by sleeping. A task that fails a criterion stops the candidate run; failed evidence is retained.

The seed has 2–3 million distinct externalized tokens counted once by the actual preserved model tokenizer. Its original bytes are checked throughout. Newly accumulated journal/artifact bytes are recorded separately as persistent evidence growth; the initial token count is never multiplied by repetitions.

Before duration begins, the matched TS/Rust preflight must pass, the product sources must still match it, and the installed candidate archive must match the current release input digest. The package, drivers, exact runtime capture and task inputs remain bound. Only disposable P14 workspaces are edited or corrupted. Runtime admission and generation use the native global custody rules. Original user state, tuned executables and profiles are not write targets.

The schedule exercises fork, branch, resume, actual WebKit reload/reconnection during a repair, a real owned model exit followed by normal native recovery, a host crash at an acknowledged idle checkpoint, and rejection/restoration of a deliberately corrupted disposable SQLite store using native recovery archives. Model and host signals require the actual launched process identities and held pidfds; a listening endpoint alone never grants control.

An external diagnostic shared library records glibc malloc_info without replacing/interposing allocator calls. The measurement is an allocator in-use-or-retained estimate including metadata and thread caches, not a pure census of live Rust objects. Native host allocator samples and complete owned process-tree PSS are separate measurements; model/helper/WebKit memory is included in PSS. Minute samples retain raw XML and process identities. Persistent disk evidence is measured separately.

The predeclared heap budget is 8 MiB/hour after a 30-minute warmup. Every sufficiently long host lifetime is fitted separately with OLS; restart resets and host absence cannot lower a lifetime's measured slope. Short lifetimes remain visible but cannot provide a passing fit. Standard errors and PSS/evidence growth are reported. This is a release stability budget, not a claim that any positive slope is a leak or that the observer has zero cost.

A completed workload remains `awaiting-claim-review`. Explicit retained reviews must cover every final assistant answer, its tool trace, the actual source diff and verifier outcome. Unsupported claims, stale authority, unexpected effects or unresolved commands block acceptance. `finalize.py` checks exact review coverage, immutable artifacts, actual duration and memory results through the P14 gate. A successful local duration result does not by itself complete P14's remaining quality, platform, signing, provenance or performance gates.

The retained `.local/p14-duration-preparation/driver_rehearsal.py` is a short scripted-provider machinery fixture; its exact tested source is archived with the public rehearsal report. `live_pilot.py` is a short actual packaged recovery rehearsal. Neither is a duration acceptance result.

Explicit failed Codex claim reviews stop the next activity after matching the completed task and rechecking its retained records/verifier hashes. This is failure termination, never a shortened duration pass. Missing or partially published reviews do not grant acceptance; finalization still requires every complete passed review. Publish asynchronous reviews atomically where possible. Operator interruption is retained as failed execution and drains the owned client through the existing cleanup path.
