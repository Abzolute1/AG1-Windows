# Defects, risks and intentional tradeoffs

No fixes were made to Cruzible. B01–B03 have reproducible probes in `evidence/measure-ag1.mjs` and recorded results in `ag1-microbench.json`; B04 has a separate fork probe. Other rows state the strength of evidence and the missing test. Do not convert a risk into a confirmed production incident.

## Confirmed defects

### B01 — Aggregate tool-result cap is applied per block

**Confirmed bug, lower-level loop.** `G:agent-loop.ts:runLoop` sums all text to detect overflow, then only truncates individual blocks whose length exceeds the full limit. The probe invokes the real loop with a 100-token/400-character cap and two 300-character blocks; the returned result retains all 600 characters. Each block is individually under the limit. Truncation also happens after result events, making event/persisted versus request representations potentially diverge.

This contradicts the documented aggregate limit, not a useful semantic choice. Normal AgentSession externalization handles some large multi-block outputs first, so this does not prove every parent-session result overflows. It still affects the lower-level Agent API and paths such as subagents. **Target regression:** combined UTF-8/text/image-aware budgeting across blocks, capture full evidence before bounded projection, one immutable final result representation per lifecycle stage; test multiple small blocks, one large block, mixed content and exact boundary. Never use unannounced truncation as the sole persistence mechanism.

### B02 — Corrupt memory becomes empty and can be overwritten

**Confirmed bug, data-loss behavior under corruption.** `A:core/memory-store.ts:readMemoryStoreUnlocked` catches parse errors and returns `emptyMemoryStore`; `writeMemoryStoreUnlocked` overwrites directly. The probe writes a truncated v3 JSON document, reads zero entries without an error and invokes the normal update path; the file becomes a valid empty v3 store without quarantine. Locking serializes callers but does not preserve damaged prior data or make replacement crash-safe.

Treating a missing new store as empty is intentional; treating a damaged existing store identically destroys recovery evidence. **Target regression:** missing vs corrupt distinction, retained original bytes/quarantine and an actionable diagnostic; temp-write/fsync/replace or transaction; fault injection at write stages, migration of v1/v2/v3 and concurrent mutation. A write must not silently replace unknown/corrupt state with defaults.

### B03 — Source text and claimed revision can describe different snapshots

**Confirmed race via deterministic injection.** `A:core/tools/source-context.ts:readSource` reads text, then separately calls `createSourceRevision`. An external edit between those reads yields old displayed lines with the new file's SHA-256. The probe intercepts one filesystem read in the isolated reference, changes `race.ts` immediately after returning its old contents, then lets normal hashing continue. Result: old evidence returned, current file contains new evidence, claimed revision validates `current`.

This violates the purpose of provenance and freshness. `source-revision.ts` checks stability during its own hashing read, but not consistency with the previous content read. **Target regression:** derive content and hash from one validated byte snapshot; detect/retry concurrent changes or mark unavailable. Test replacement/rename, same-size edits, symlink swaps, CRLF, Unicode and multi-file capsules. Do not “fix” by removing freshness gates or hashing only selected normalized lines.

### B04 — Forked journals retain references to an inaccessible parent artifact store

**Confirmed at the storage boundary; runtime call chain traced.** `AgentSessionRuntime.fork` calls `SessionManager.createBranchedSession` and constructs a new runtime with the new session ID. The branch operation copies journal entries but does not copy/adopt their artifact closure. `AgentSession` creates its store under the new ID; `ArtifactStore.get` reads only that store and enforces session ownership. There is no parent-store resolver in these paths.

`evidence/probe-artifact-fork.mjs` uses the real branch operation and the same store-root construction: the child branch retains the artifact reference, the parent's evidence is readable, and the child's read fails with ENOENT. This probes the persistence/store boundary rather than running a model through the full facade. It establishes a reachable failure when forking history that includes externalized evidence. Merely copying record files is insufficient because session ownership and authenticated cursor keys must also be respected.

**Target regression:** fork a session with source capsules, compaction/episode/tool artifacts, binary evidence and active cursors; prove the child can resolve its authorized historical evidence after restart and parent archival/deletion policy. Choose shared immutable blobs with explicit cross-branch authorization/reference ownership or a complete remapping/import transaction; never leave dangling references or weaken cross-session access checks. Apply the same closure check to JSONL-only import/export. Retention must not delete evidence still referenced by another branch.

### B05 — Removing label records during a fork breaks message ancestry

**Confirmed during P10 implementation against the pinned reference, in disposable files.** `A:core/session-manager.ts:createBranchedSession` removes historical label entries and appends resolved labels, but leaves retained messages pointing to the removed label IDs. `walkBranchPath` stops when a parent is absent. A message following an interleaved label therefore loses its earlier ancestors from the fork's traversed history even though those records remain physically present.

`tools/probes/runtime_session_fork_reference.mjs` captures six real SessionManager cases in `fixtures/runtime/session-fork-oracle.json`. Five label-bearing cases contain a dangling parent and omit the first message from `getBranch`; the plain case retains both messages. The captures also establish current label updates, removal and re-addition ordering, and exclusion of labels whose targets are outside the selected branch. This is a history-loss defect, not an intentional label display rule. Cruzible remains unchanged.

**Native correction and regression:** `SessionSeed::RuntimeFork` creates a new header, retains the source's resolved-label behavior, and reconnects retained entries through the previous retained ancestor before appending new labels. The original parent journal is unchanged. `product/crates/ag1-storage/tests/runtime_fork/mod.rs` compares all six source captures with that explicit ancestry correction and verifies complete traversable history, empty-fork authority, atomic origin/receipt custody, lost acknowledgements and exact retry after the parent advances. The lower-level lossless `SessionSeed::Fork` primitive remains available for storage compatibility; the product session transition uses `RuntimeFork`.

### B06 — Discarding an executing plan can restore its previous state on reload

**Confirmed during P10 against the pinned plan state functions.** `A:modes/interactive/interactive-plan-artifacts.ts:updateInteractivePlanArtifactStatus` retains execution-step fields when changing an executing plan to discarded. Its parser rejects those fields on non-executing plans. The latest-plan lookup then skips the new discarded record and returns the older executing record. The interactive clear command uses this status update without clearing the execution fields.

`tools/probes/runtime_plan_state_reference.mjs` captures the actual transition, reload result and all 64 source status-transition decisions in `fixtures/runtime/plan-state-oracle.json`. No original source is changed. The Rust plan reducer clears execution fields when leaving executing state. Its regression checks that a discarded plan remains discarded, exact plan/revision references distinguish independent threads, and an invalid transition or clarification index is rejected. This is a domain regression; the complete native plan command workflow is still being implemented.

### B07 — Completing one plan step can hide its review and progress on reload

**Confirmed during P10 against the pinned plan functions.** `A:modes/interactive/interactive-plan-artifacts.ts:recordInteractivePlanStepExecutionReview` clears execution-step fields after an assistant review reports completion, but retains `executing` status when other steps remain. Its parser requires those fields for executing plans, so the latest lookup skips the new review and restores the older record with no completed steps.

`tools/probes/runtime_plan_workflow_reference.mjs` reproduces the state update and reload with a two-step plan, alongside structured submission and review cases in `fixtures/runtime/plan-workflow-oracle.json`. Rust moves that plan back to `accepted`, matching the source's manual step-completion behavior, and preserves the recorded review and next unfinished step. All steps complete still yields `completed`. Reviews remain assistant-reported workflow progress, never host verification evidence. Original source is unchanged.

## Already-corrected regressions are parity requirements

Existing tests for mid-loop compaction, async persistence draining, stale retry replay, partial tools, duplicated result events, dynamic provider/tools, resource reload, listener exceptions, file mutation queues and Windows pipe close hangs describe behavior already protected by the reference. Preserve those fixes rather than listing every test name as an open defect. For any future suspected issue, require a failing scenario and an explanation of intended behavior before changing semantics.
