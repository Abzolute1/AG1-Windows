# Native session composition — P10 in progress

`ag1_core::runtime::SessionRuntime` owns the current committed branch, configuration and request/tool/persistence barriers. `ag1_platform::session::NativeSession` executes its actions through real storage, context compilation, HTTP transport and the host's shared scheduler. Neither module imports a terminal, frontend or TypeScript AgentSession.

The embedding supplies an existing `Store` and authorized artifact origin, an explicit workspace, a shared bounded `BlockingPool`, the shared P06 `Scheduler`, a configured `ProviderHttp`, a `ProviderResolver`, and a `ToolRunner`. Resolver input is the captured model/context; only host configuration may resolve credentials and endpoints. All roots, summaries and delegated generations must use the same scheduler authority. There is no session-local scheduler constructor or model retuning.

`run` accepts a user message and an optional caller generation budget. It captures the committed branch, retains original context through `ContextStore`, resolves the provider, acquires a permit and rechecks admission immediately before dispatch. A model/tool/task change during preparation causes rebuilding. Memory and source revisions are revalidated after asynchronous provider resolution and scheduler admission; a changed witness also rebuilds the unsent request. Provider progress is separate from journal acknowledgement. Client listener panics cannot interrupt internal processing. Standard provider messages use the same projection as the optional extension host.

User instructions append durable task state after the user message, preserving the first objective and skipping repeated instructions. Request preparation rebuilds task, runtime, inspection and episode addenda from the current branch, anchors them to the latest user message, and retains that complete unreduced request as an artifact before compilation. This augmentation never changes the journal's user messages. Project memory augments the captured system prompt through the existing P08 projection; corrupt memory stops preparation for explicit repair. Successful tool results with valid, matching inspection evidence append a separate structured record only after result acknowledgement. Host task updates use the same storage owner via `append_task_state`.

`install_resources` accepts a completed P09 resource snapshot and the host's tool registry. It builds the P08 base prompt from captured project instructions, system overrides, appendices and skill metadata, then publishes the resource fingerprint and configuration through the journal owner. `Configuration.prompt` optionally retains these captured inputs; model and tool changes rebuild the base prompt, and mismatched registry/schema definitions reject the update. Resume rebuilds from the host-supplied resource configuration instead of trusting a cached prompt string. Runners that supply their own complete system prompt can keep this field `None`.

Every returned parent provider snapshot, including partial failures, is retained as a `runtime-provider-output` artifact before error normalization, message validation or journal append. Accepted assistant messages link it through `nativeOutputArtifact`. Artifact failure drains generation ownership but leaves a sticky persistence fault that blocks subsequent requests. Output rejected by journal byte or tool-identity limits remains searchable and survives store reopening; it never executes tools. This preserves the data returned by the provider reducer, not wire fragments rejected earlier by transport/framing limits.

`compact` reserves the session boundary before interrupting a parent. It waits for accepted output and tools, retains the original journal/request and exact compaction trajectory, then runs same-model history and split-turn summaries sequentially through the shared scheduler. These isolated requests have no tools, cache retention or inherited conversation history. Summary deadlines cover resolver preparation, queueing and transport; the caller supplies the reference default of 900000ms separately from parent reasoning settings. Request resolvers must permit safe cancellation of preparation and cannot dispatch inference themselves.

Only the acknowledged compaction record advances the context epoch. Original journal entries remain intact, and a durable suffix appended during summarization appears once in the next context. Model/tools/thinking changes reject stale summaries. Restart recovers the committed epoch, including after a lost acknowledgement. The request boundary converts compaction, branch, custom and direct-shell messages to the pinned provider-facing shape without rewriting their journal roles.

Automatic context pressure can trigger compaction before dispatch. Prompt-too-long summary responses retry reduced analysis groups while retaining their original trajectory and every returned attempt as evidence. On summary failure or timeout, automatic compaction may commit the pinned deterministic recovery checkpoint with raw-artifact provenance; cancellation, stale state and custody failures cannot take that path. A quarantined summary transport still blocks parent continuation and requires host reconciliation. Manual failures return their error.

Ordinary provider retries use the pinned classification and backoff rules, with explicit caller settings (defaults: enabled, three retries, 2000ms base delay). The native HTTP status marker has the same precedence as the SDK's structured API marker. A single retry/compaction arbiter and captured stamp protect backoff and final dispatch; manual compaction preempts the waiting parent. A known terminal response is required before retrying. The owner atomically selects the failed attempt's parent through the new journal branch port, retains the abandoned records, and waits for acknowledgement before preparing the replay. Failed unsent preparation restores the original branch only if the exact owner/epoch/configuration still matches. New work and replacement owners cannot be overwritten by that rollback.

Provider-reported context overflow uses the same durable branch exclusion, followed by one compact-and-retry attempt. Another overflow stops the parent; successful assistant completion resets that guard. Silent overflow from successful stop responses now enters that same recovery path. Only the terminal leaf response is excluded; earlier tools and later journal mutations cannot be rolled back. A second silent overflow stops with an explicit recovery failure. Full queued-message and extension recovery behavior also remains part of P10's pending parity gate.

`NativeToolRunner` (also exported under the earlier `FileRunner` name) composes read, write, edit, append, preview/apply, listing, grep/find, repository orientation, Git diff, shell, background jobs, web search and web fetch through P09 services, plus native source capsules, task state, todo plans, runtime observations, episodes, project memory and immutable artifact recovery through P07 storage and reducers. `NativeAdapters` holds explicit host capabilities; missing services cannot become executable through model tool selection. Each batch rebuilds the active registry from the latest selected names and available adapters. Up to eight consecutive read/list/search/diff calls execute concurrently; mutations form ordered barriers. Preparation and approval run in source order, including shell prefix/template expansion before policy. Results and inspection records reach the journal in source order. Revision changes invalidate pending execution, and cancellation drains owned shell processes before committing the final result. `ApprovalHandler` belongs to the host; `RejectApproval` never grants approval. Approval leases stay within P09's five-minute bound while explicit tool deadlines remain separate.

`NativeWeb` binds scoped P09 web services to a host-owned Tokio handle. The native bounded blocking worker drives their futures and bridges parent cancellation without a detached task; completion waits for the HTTP cancellation path. Web policy, credential and service-incarnation stamps remain P09 authority. The host must keep the executor alive through drain and replace scope-bound services after an epoch/configuration change; stale service epochs fail without network access. `ToolSelection` captures current selected names and research compression with the committed batch scope. Compression uses the current model window and successful usage plus trailing messages (fresh attribution after compaction until post-compaction usage exists). Search dates use the injected clock's Unix milliseconds. Web response bytes retain their original untrusted evidence before transcript projection.

`MemoryTools` uses the same workspace memory namespace as request assembly, with the prepared document hash in its approval target and CAS at publication. List/search/add/update/remove/clear reuse the reference presentation and P07 reducers; source-bearing notes are revalidated through the actual `SourceService`. The admitted request supplies the exact memory IDs used for “injected last turn” markers. Invalid commands and stale preparation produce settled results with no effect; storage commit/ack failures propagate as uncertain mutations for inspection. Corrupt imported memory cannot be cleared or overwritten implicitly. The integration's reference capture exposed and fixed a native reducer bug where updating/removing a note inserted `archived: null` when no archive existed.

`ToolOutcome.execution_settled` distinguishes drained execution from effect classification. General shell commands retain `Effect::Unknown` because their complete filesystem effects cannot be enumerated, even when a terminal process result and raw output are durable. The session can continue after that terminal result; it does not reexecute recovered receipts. Missing execution settlement stops continuation for reconciliation. Background-job completion notices remain pending until a future session notice commit acknowledges them; collection and retirement across epoch changes are still pending runtime integration.

Provider `GenerationLimits.overall_ms = 0` now disables the overall watchdog. Zero prefill/idle limits also remain disabled. These values create no synthetic future deadline; cancellation and byte limits still apply. Nonzero watchdogs retain their configured behavior.

Call `cancel()` and continue polling the running future until it drains accepted work. Dropping a future can leave unresolved writes/effects and requires reconciliation. `settled()` includes the exact provider ticket: a quarantined transport remains unsettled even after local output processing ends. `pending_transport()` is a host-supervisor capability; only terminal evidence or verified owned process exit permits scheduler reconciliation. It is not a renderer command.
