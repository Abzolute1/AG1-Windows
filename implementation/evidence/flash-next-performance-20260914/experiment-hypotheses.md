# Experiment hypotheses

All proposed changes below remain unproven until measured. No original source/configuration is edited.

1. **Thread placement:** Zen3 has two6-core CCDs. Six decode threads stay within one CCD, while12 physical or24 logical batch threads may pay different barriers/cross-CCD traffic. Compare6/12,8/12,12/12 against original12/24, then polling. Quant/backend execution remains unchanged.
2. **Batch and expert placement:** original warm review prefill moves severalGiB/s over PCIe, while host CPU utilization is near one core. Larger microbatches amortize selected expert-weight transfers; GPU workspace may require moving more expert layers to RAM and harm decode. Test those variables separately and label tradeoffs.
3. **PLE gather threading:** upstream ggml-cpu.c schedules GET_ROWS with exactly one task despite an already partitioned multithread-capable quantized row loop in ops.cpp. Its comment targets small GPU-offloaded embedding gathers. Flash-Next instead gathers16,384 rows per1024-token microbatch from a35.76GiB sparse table. A thresholded task count for large lazy embeddings could overlap independent page faults without slowing single-token decode. Compare original path, threaded path, and upstream direct-pread path; verify exact rows/logits and real prompt timing.
4. **PLE explicit reading:** upstream PR28136 sorts/deduplicates row reads and creates per-gather worker threads with pread. Buffered pread still uses the OS page cache; it is not synonymous with O_DIRECT. Compare cold table reads, warm reuse, distinct new text and retained model residency on this SATA disk.
5. **History lookup:** current upstream replaces an earlier scan/rebuilt hash-map implementation in get_prev_tokens with indexed sequence-position lookup. Determine whether the exact original bundled source has the old path and benchmark at long context.
6. **CPU MXFP4 layout:** MXFP4 down projections account for19.92GiB. Upstream has an AVX2 eight-row repacked kernel and MUL_MAT_ID support, but explicit CPU+mmap placement may bypass it. A pure CPU_REPACK experiment could help decode yet prevent GPU prefill offload. Do not accept that tradeoff automatically; any dual representation/cache must preserve original bytes and demonstrate a memory/performance benefit.
7. **Runtime speculation:** original has none. Its older recurrent rollback may serialize state to host. Compare ngram-mod/map strategies, draft depth and fresh-process repetitions; inspect newer on-device rollback and compatible MTP heads. Count accepted/proposed tokens, CPU/GPU copies and exact-edit correctness. Preserve PLE convolution history as well as GDN recurrence when rolling back.
8. **CPU expert caching / GPU staging:** previous35B specialized Q4_K/Q5_K/Q6_K staging is inapplicable as written to this mixed MXFP4/IQ2_S/IQ1_M file. Any transfer or expert-cache port needs type/stride-aware implementation, reference output checks and real inference measurements.
9. **Model alternatives:** current mixed quant uses51.2B Q5_1 PLE parameters,40.265B MXFP4,20.133B IQ2_S,60.398B IQ1_M and4.862B Q8_0 parameters. Published Unsloth UD-IQ4_XS has a smaller/lower-precision PLE table but larger main weights. It cannot automatically be called a permitted strict quality upgrade based only on its name or total file size. Higher precision or lossless alternate storage/layout must fit the full resident working set, not merely available disk.

10. **Projection-specific placement:** the current profile puts all expert projections from six entire layers on GPU. Given the mixed quantizations, it may be better to spend the same VRAM on more IQ1_M gate/up projections or on MXFP4 down projections. Construct explicit per-tensor placement rules, keep every expert and layer, and compare CPU kernels/transfer overhead and full inference; do not assume equal tensor bytes imply equal compute cost.

Cold-PLE comparisons will selectively evict only the read-only dedicated shard2 from the OS page cache between process starts, then verify residency with mincore. This does not alter model bytes or globally flush caches. SSD/controller cache state remains uncontrolled and is explicitly not called a cold boot.

11. **Persistent expert slot pool:** memoriaru/llama.cpp `moe-expert-pool` head1582fccab9cfadb423e653de3c36516d02d72d63 implements an approximately700-line backend-independent slot cache/remap path. Unlike the earlier35B custom CUDA cache, it uses existing MUL_MAT_ID kernels and may cover this mixed quant without new kernels. Its latest fix replaces a two-element expert-tensor collector that overflowed for separate gate/up/down layouts. Any test must include that fix, IQ1_M/IQ2_S/MXFP4 reference comparisons, remap ordering on cache misses, real context, memory headroom and actual AG1. This is a promising candidate, not an accepted optimization. Source discussion: https://github.com/ggml-org/llama.cpp/discussions/28248 .

Direct-read patch inspection correction: the downloaded PR diff creates and joins worker threads per gather; it does not have a persistent pool. If thread creation is measurable, reusing workers is a separate source-level experiment. The PR diff targets the newer lazy_read loader abstraction, so porting into the Sep11 Unsloth tree may require explicit loader adaptation.

Expert-pool source review found two specific issues to test before trusting its hit-rate reports:

- **Batch-aware eviction:** update_expert_pool processes selected expert IDs in increasing order and refreshes existing hits only when it reaches them. An early miss can therefore evict an already-resident expert also needed later in the same batch, causing an unnecessary second upload. Example: two slots contain5(oldest),6; batch needs4,5. Sequential LRU uploads4 after evicting5, then uploads5 after evicting6; protecting all resident batch hits first needs only the4 upload. The proposed two-pass protection does not alter weights, routing or outputs. Quantify real avoided uploads, not merely hit counts.
- **Duplicate update accounting:** pool updates are triggered at the map GET_ROWS and also at pooled MUL_MAT_ID. The same pool/routing may be refreshed twice in one graph execution, inflating apparent hit rate and repeating CPU bookkeeping. Instrument first. If confirmed, cache the update epoch plus original routing tensor per pool, and skip only an identical already-completed update within that graph execution. Reset/increment epochs across graph executions to prevent stale mapping reuse.

Both are isolated source experiments pending real-model benchmarks. The stock pool remains a separate control.
