# MCP scoped trust — core implementation in progress, 2026-09-12

C3 has begun in the ordinary core registry/authorizer. This is a development slice, **not a completed trust checkpoint or a production installation**. The installed release remains the [verified C2 OAuth build](MCP-OAUTH-PROGRESS.md). Durable manager grants, effective launch/endpoint binding, native review/edit/revoke controls, containment and project configuration intake still need implementation and acceptance. Full MCP A–F remains active.

The native `ReviewedPolicy` witness is not deserializable. It binds the selected capability's server UUID, canonical scope, configuration, credential profile/generation, connection, protocol, kind/name and complete metadata digest. Conversation ownership remains independently enforced. Peer metadata and generic chat bypass cannot manufacture the witness. Registry copies retain its shared revocation state; a revoked witness rejects preparation, approval reuse, approval answers and execution-ticket validation even against an old registry snapshot. Different witnesses with equal numeric revisions cannot substitute for each other. Native manager integration must serialize revocation with the existing send gate and validate the effective target before issuing witnesses.

Bounded rules support explicit all-argument review or exact top-level scalar equality without coercion; missing fields differ from explicit null. Rules are limited to 16 selector fields, 4 KiB scalar strings, 16 KiB per rule, 32 rules and 64 KiB per policy. Deny, ask and higher consequence classifications take precedence over overlapping allow rules. Restricted defaults ask. Disable writes denies unmatched, unknown, mixed/write and consequential cases. Planning and headless reject writes and cases needing confirmation; planning's explicit read block also remains stronger than an MCP read grant.

Native host risk, user-reviewed effect and server annotations remain distinct. Native consequential classification cannot be lowered by a reviewed read/write grant. A conservative native heuristic also escalates operation names and actual arguments containing destructive, administrative, credential/access, payment or publication signals. This heuristic only raises risk; it neither proves a read safe nor guarantees remote behavior. Consequential cases require an exact fresh shared-authorizer confirmation even in bypass mode. No unrestricted Trusted mode is introduced; the future UI must summarize explicit grants.
