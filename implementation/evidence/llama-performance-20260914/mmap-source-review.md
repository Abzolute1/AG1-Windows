Source references below are relative to that tree unless stated otherwise. This review ran no GPU work, builds or model-file modifications. The parent subsequently planned to restrict shim registration by exact GGUF-backed read-only VMA coverage; that restriction was not in the initial shim inspected here.

## What registration changes

The loader substitutes ordinary CPU buffers for CUDA host buffers when using mmap (`src/llama-model-loader.cpp:1211`). Model loading then wraps each CPU context's minimum-to-maximum tensor file range in a CPU buffer (`src/llama-model.cpp:1594`, `:1608`). The mapping remains the storage owner; the CPU buffer does not own its pointer (`ggml/src/ggml-backend.cpp:2591`). Registering that existing read-only range with CUDA can make host-to-device transfers eligible for pinned-memory behavior without copying or modifying the model file. It does not relocate expert weights into VRAM, change their quantization or make CPU arithmetic faster by itself.

CUDA toolkit 13.3 documentation in `/opt/cuda/include/cuda_runtime_api.h:5069` says registration adds the range to CUDA's host-memory tracking and warns that excessive page locking reduces memory available for paging. On systems using host page tables, it may populate rather than page-lock pages. Read-only host mappings require `cudaHostRegisterReadOnly` on platforms without that host-page-table capability; support is queryable through `cudaDevAttrHostRegisterReadOnlySupported` (`:5110`). Unregistration must use the exact original base pointer (`:5173`). Record registration success, bytes and duration rather than assuming all requests succeeded.

The fork already exports optional provider functions named `ggml_backend_register_host_buffer` and `ggml_backend_unregister_host_buffer` (`ggml/src/ggml-cuda/ggml-cuda.cu:5521`). Their implementations use Portable plus ReadOnly flags and are gated by the presence of `GGML_CUDA_REGISTER_HOST` (`:4669`). A source integration can use these provider functions without linking the model loader directly against CUDA. The unregister function checks the environment again; any integration must keep the opt-in environment stable through cleanup or change the experimental helper to unregister based on recorded ownership rather than a mutable environment check.

## High-value shim hazards

1. **Provenance:** the initial hook registers every nonempty CPU `buffer_from_host_ptr` allocation. That API is broader than read-only GGUF weights. Restricting it to the exact requested primary GGUF's read-only VMAs, with complete pointer-range coverage and overflow checks, is appropriate for a bounded experiment. A failed or incomplete provenance check must skip registration. Canonical path/device/inode identity is stronger than a substring path match. File mappings can be split into multiple VMAs, so checking only the first byte is insufficient.
2. **Teardown order:** the initial shim unregisters before calling the original `ggml_backend_buffer_free`. The original function first invalidates users of host weights (`ggml-backend.cpp:219`); the fork's MoE-cache invalidation waits for active references and in-flight source users (`ggml/src/ggml-cuda/moe-cache.cu:3020`). Unregistration must follow that drain. For a verified CPU buffer-from-pointer, calling original free first and then unregistering the saved pointer is a narrow possible shim repair because this buffer's `free_buffer` callback is null and does not unmap storage. This ordering should not be generalized to owning buffers. A proper source-owned registration lifetime is preferable.
3. **Registration overlap:** per-buffer ownership does not automatically handle overlapping address ranges or shared OS pages. Two contexts may wrap different spans of one mapping; registrations can fail or conflict at page boundaries. Track exact registration bases and successful ownership. Do not unregister somebody else's existing registration after a failed registration. A proper integration should coalesce nonoverlapping page intervals per file and keep a single owner/refcount for shared ranges.
4. **Exceptions and logging:** after a successful CUDA registration, insertion into the shim's unordered map can throw. The initial code lacks a rollback for that allocation failure. A registration owner must be established exception-safely, and cleanup errors must remain visible. Clearing the CUDA last-error state to recover a failed registration also means the shim should not silently relabel an unrelated asynchronous CUDA error as a harmless pinning miss.
5. **Lifecycle scope:** CUDA runtime/provider libraries must remain loaded while their unregister functions can be called. Model/session shutdown must first stop requests and join any users of the mapped weights. The shim's registry mutex protects its map, not the lifetime of external asynchronous readers or mappings.

## Verified mapping destruction order

An initially suspected ordinary cancellation ordering problem was checked and **not confirmed**. `src/llama.cpp:307` constructs the model loader before the `model_ptr` at line 311. On cancellation or an exception, reverse destruction frees model-owned backend buffers before the loader-owned mappings. On successful loading, mappings move into the model at `src/llama-model.cpp:1687`. In `llama_model::impl`, mappings are declared before `ctxs_bufs` (`:1032`, `:1039`), so reverse member destruction frees buffers before unmapping storage. These two paths support registration ownership that ends after buffer/cache teardown and before mapping destruction.

This does not excuse the shim's current pre-invalidation unregister order. Nor does it prove lifetime safety for arbitrary users of `buffer_from_host_ptr`, partial manual teardown, future interior trimming, or library unload. Those need explicit handling in the integrated design.

Current final loader trimming removes only the prefix before `mmaps_used.first` and suffix after `mmaps_used.second` (`src/llama-model-loader.cpp:1683`). `llama_mmap::unmap_fragment` rounds the start upward and end downward to full pages (`src/llama-mmap.cpp:479`). Once every referenced CPU tensor has been allocated, its context registration span should lie within the preserved minimum-to-maximum CPU tensor envelope. Retaining that invariant makes current outer trimming compatible with registration; assert/check it rather than relying on tensor ordering.

The CPU registration is a **span**, not a list of CPU tensor extents. GPU-only tensor bytes and padding can lie inside it. Those holes are pinned along with useful CPU weights and cannot be independently unmapped or discarded while that registration remains active. Early loading before the global retained envelope is complete requires a precomputed interval plan; the incremental `mmaps_used` state alone is not sufficient.

## Minimal proper source integration

Use an isolated source tree and an opt-in model-load setting/environment control. Do not change default placement or loading mode.

- At model buffer creation, where mapping/file/context provenance is known (`src/llama-model.cpp:1594`), compute eligible read-only host intervals from the actual CPU tensors. Resolve the selected CUDA provider's registration capability. Keep ownership independent of backend buffer handles and remember only successful registrations.
- Store RAII registration owners in `llama_model::impl` **after mappings and before `ctxs_bufs` in declaration order**. Reverse destruction then becomes buffers/cache invalidation, registrations, mappings. The existing loader-before-model construction also handles failed loading. Each owner records base, size, provider/unregister function and active state; construction must roll back on allocation failure.
- For an initial narrow patch, register coalesced CPU context spans and preserve their entire page envelopes. This keeps changes small while exposing wasted pinned holes as measured bytes. Later finer intervals can reduce pinned RAM but need shared-page accounting, range coalescing and validation of every transfer's covered address range.
- Keep registration soft-failing: leave ordinary mmap behavior intact if unsupported or resource-limited. Do not disable original tensor placement, repacking decisions or correctness checks to make registration succeed. Report pinning separately from model allocation and ensure backend unload occurs after RAII cleanup.
- Preserve existing synchronous loading first. If adding async mmap uploads later, each registered source interval needs a recorded completion event and must stay mapped/registered until the event and any validator finish. Drain on success, cancellation and exception before unregistration or unmapping. Do not reuse staging/event patterns without adding exception-safe ownership.

This design is a proposal, not an implemented or validated source optimization.

## Peak-RSS opportunities and required proofs

**Strongest finding:** loading currently calls `ml.init_mappings(true, ...)` (`src/llama-model.cpp:1557`). On Linux that adds `MAP_POPULATE` for the whole file and requests `POSIX_MADV_WILLNEED` (`src/llama-mmap.cpp:448` through `:464`). A whole-file population peak can therefore occur before individual GPU uploads begin. Dropping pages only after uploads can reduce later RSS but cannot undo an already recorded peak. Meaningfully reducing peak mapped RSS may require disabling whole-file population and replacing it with bounded, sequential read-ahead. That is a distinct load-time experiment, and cold/warm filesystem-cache conditions must be recorded.

Current mmap GPU uploads use synchronous `ggml_backend_tensor_set` (`src/llama-model-loader.cpp:1574`). For the CUDA implementation, that enqueues a copy and waits on the same per-thread stream before returning (`ggml/src/ggml-cuda/ggml-cuda.cu:855`). Thus, for this verified CUDA path, return establishes completion of that upload's source reads. `check_tensors`, however, launches validators asynchronously (`src/llama-model-loader.cpp:1557`) and joins them only later (`:1667`); an upload finishing does not prove that validation has finished reading its source.

For early release of GPU-only source pages, precompute a per-file live-page plan across **all contexts and aliases**. A page is eligible only when all of the following are established:

- Every tensor consumer requiring that page has completed loading or conversion; duplicate/tied tensors and later contexts are accounted for.
- Every asynchronous upload, CPU repack/copy and validator reading the page has completed, including failure/cancellation cleanup.
- No CPU-resident tensor, lazy row reader or other retained mapping user requires it.
- It is outside every active CUDA registration and mlock range, including page-rounded boundaries and GPU-only holes inside retained CPU spans.
- Only full pages are released; pages shared with neighboring live tensors remain intact.

After these proofs, `unmap_fragment` can permanently release dead source intervals while retaining its fragment bookkeeping. This is stronger than advice and must never target a page that a later loader step will access. Alternatively, process-local `MADV_DONTNEED` on eligible ordinary read-only mapping pages can reduce resident mapping pressure while keeping addresses valid; it does not guarantee removal of the underlying file from the system page cache or an equal reduction in machine-wide RAM usage. Do not use file-wide cache eviction or global cache flushing as part of this optimization.

A low-complexity first experiment is bounded population/read-ahead plus releasing completed GPU-only prefix/suffix intervals outside the full precomputed CPU registration envelope. Interior holes should remain deferred until interval ownership and validator/upload completion are implemented correctly. Record peak RSS/VmHWM, steady RSS/PSS, pinned bytes, system available memory, page faults, load time and first inference latency; mmap can shift work into first use rather than eliminate it.

## Recommendation

Continue the restricted registration shim only after correcting teardown order and documenting exact coverage. Use it to test the transfer-speed hypothesis without changing weights. For a lasting integration, prefer model-owned RAII registration and explicit retained intervals. Evaluate bounded mmap population separately: it addresses peak host-memory use, while registration addresses DMA eligibility and may increase locked memory. Neither is an all-round improvement until repeated real inference, load-time and memory measurements support it.
