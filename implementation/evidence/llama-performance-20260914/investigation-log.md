## Measurement method

`bench-v1.py` records the initial measurement harness; the working harness later adds read-only NVML PCIe counters without changing requests. Each server process is owned and stopped by the runner. GPU inference runs sequentially, never alongside another model.

Fixed prompts were formatted/tokenized once by the original server and saved with hashes in `prompts.json`. Every build receives the same token IDs and read-only GGUF file. Actual HTTP streaming inference uses `/completion`, greedy sampling (temperature0, top_k1, top_p1, min_p0, seed777), repeat penalty1, prompt caching disabled, slot0, and256 generated tokens for performance requests. Native timing `cache_n` is checked so reused prefixes do not inflate prefill speed. TTFT measures wall time from request start to first nonempty streamed content. Load time runs from process creation to successful health readiness and includes the loaded projector and normal warmup; filesystem cache is not globally dropped, so it is a warm-filesystem measurement, not a cold-boot disk benchmark.

Workloads: a957-token retry-code review, a9,154-token service inventory plus code review, and a9,051-token exact structured extraction with up to768 generated tokens. The extraction must reproduce25 independently computed fields across five services as exact JSON; it is a bounded correctness check, not a comprehensive quality evaluation. Long-context checks are tracked separately. Performance answers are intentionally length-limited, so their256-token excerpts do not represent complete code-review quality evaluations.

Resource samples are taken every0.5 seconds. CPU polling can consume CPU without useful work, and GPU utilization is not a measure of achieved FLOPs. Later NVML PCIe measurements sample20ms counter windows and should not be treated as full-request byte integrals. Background activity, clocks and temperatures are retained in telemetry; no compiler or large file hashing runs alongside timed inference. Three repeated requests per workload are summarized by medians. Final comparisons must repeat useful candidates across server restarts and document small gains as uncertain until they exceed noise.

## Upstream research and source hypotheses

The installed build already enables fused GDN, CUDA operation fusion, target-specific CUDA compilation and CUDA graphs. Newer upstream removing the non-fused GDN fallback is therefore not sufficient reason to predict a speedup: [upstream PR27877](https://github.com/ggml-org/llama.cpp/pull/27877).

Upstream v0.4.0 points to commit `427291b5b34cd914a31b3fd3b61a68f6184f4b9f`: [release](https://github.com/ggml-org/llama.cpp/releases/tag/v0.4.0). The latest master API snapshot is `ad6c66839af3c5646fba8c6c2e2087a1e4e38948`; its latest BF16 fallback change targets devices lacking native BF16, not the target GPU: [PR28846](https://github.com/ggml-org/llama.cpp/pull/28846). Pinned API responses are stored locally. No speed claim follows from revision age alone.

Recent experimental MoE caches exploit temporal expert reuse, but published speedups use different hardware, models, context and memory placement: [LRU cache draft PR27861](https://github.com/ggml-org/llama.cpp/pull/27861), [persistent slot pool discussion28248](https://github.com/ggml-org/llama.cpp/discussions/28248). The original TurboQuant fork already has its own `--moe-cache` path with repacking and VRAM tradeoffs; importing an unrelated cache is not automatically beneficial. The CUDA graph optimizer is an opt-in Q/K/V branch optimization, not general GDN parallelism. Detailed local source locations and profiling proposals are in `source-review.md`.

A reported load-mode pinning problem concerns memory pressure and swapping on much larger host-resident models; it does not establish a problem on the benchmark host with ample RAM: [issue26110](https://github.com/ggml-org/llama.cpp/issues/26110). Load/mmap changes require measurement here, not copying another machine's recommendation.

## Architectural limits and untested directions

Large prompt batches do not make autoregressive output independent: prompt tokens are known in advance, whereas each new output token normally depends on the preceding result. RAM placement frees VRAM for larger activation buffers but increases the CPU expert work on every generated token. This is why prompt throughput and generation throughput move differently.

The benchmark topology exposed one NUMA node, so NUMA interleaving is not an established optimization here. The affinity flags do not actually bind the server workers; initial inference placement must be treated as unrestricted, including SMT siblings. Four-thread and six-thread tests examine CPU scheduling without changing the system governor. Continuous batching can improve aggregate multi-user throughput, but would not answer this single-user, single-slot latency task and could consume the preserved90k context budget differently. No global scheduler, governor, power-limit or driver change was made.

The selected-expert copy and CPU/GPU split paths remain candidates for deeper overlap work. However, removing ordering waits without lifetime/alias proofs could corrupt recurrent state or reused buffers. The duplicate-destination-wait candidate is documented in source-review.md; the observed tensor-copy API category occupies only about3% of decode host wall time and includes necessary work, so no large gain is established. No novel source optimization is claimed or merged. The isolated native CPU backend and CUDA scheduling shims were the source/build experiments actually measured.

## Quality evaluation boundary

The free-form source-code reviews are useful performance inputs but are not fully correct answers. The original review asserted broad atomic/concurrency guarantees and described duplicate pending admission as a current-status response, whereas the supplied source returns DurabilityUnknown if a duplicate has no settled result. The optimized review described loading as non-interruptible and described quarantine as waiting, whereas the source includes cancellation/recovery paths and cancels the queued ticket when quarantine is observed. These excerpts are truncated at256 tokens and both overstate guarantees. They do not justify claiming semantic quality equivalence or a universal regression from a single changed phrase. Larger batches can change floating-point reduction order and therefore greedy token choices even with the same weight/KV precision. Exact code-fact questions were added to compare these behaviors using independently checked answers.

Correction to earlier `--no-host` interpretation: source tracing distinguishes host pinning from repacking. The measured no-host slowdown cannot be attributed solely to disabling repacking. `--no-host` removes CUDA_Host selection and may select Q4 CPU_REPACK, whose buffer lacks the host predicate needed by the scheduler's large-batch GPU offload gate; Q5/Q6 then use canonical pageable CPU storage. An AUTO cache with an environment budget can preserve extra-buffer selection. Cache compute itself accepts at most eight tokens; large prefill remains on the existing scheduling path. These distinctions motivate a broader expert-cache test, without assuming it will improve speed.
