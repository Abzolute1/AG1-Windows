C2 supports **native public-client pre-registration**: the user selects an advertised authorization server and enters an existing client ID registered for AG1. The client must allow authorization code with S256 PKCE, token authentication method `none`, and AG1's literal loopback callback with an ephemeral port. Issuer/resource/client bindings remain native and are checked again before authorization and token exchange. Unsupported registration or confidential-client authentication fails visibly without fallback to provider or GitHub credentials.

This is the supported registration strategy for the C2 checkpoint under task §7. It does not claim every optional authentication mechanism. The current MCP specification includes user-entered pre-registration, recommends Client ID Metadata Documents, and retains Dynamic Client Registration as an optional, deprecated compatibility mechanism. Its selection priority applies to clients supporting all mechanisms. [Current registration requirements](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/client-registration.mdx)

AG1 has no established, owned public HTTPS client-metadata URL in this project. Fabricating one or publishing metadata under another application's identity would not establish CIMD support. Hosting such a document and configuring its ownership/redirect policy are not part of this native checkpoint. Automatic registration therefore remains an explicit product limitation; the UI gives the supported manual route. This does not remove trust, public registry discovery/setup, or any other A–F requirement.

If DCR compatibility is added, reserve and retain the actual callback listener before the reviewed registration POST, request `application_type: native` and public-client authentication, validate the returned client/redirect/grant binding, and bind cancellation and stale-review checks to the manager. Registration failures must not trigger an unreviewed retry. [RFC 7591](https://www.rfc-editor.org/rfc/rfc7591.html) and the current MCP registration page govern that separate implementation; no DCR behavior is claimed by the existing tests.
