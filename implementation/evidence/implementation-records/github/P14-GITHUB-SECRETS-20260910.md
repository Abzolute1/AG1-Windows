## Implemented

Typed `secrets.set`, `list`, `get`, `delete`, `repositories` and `set_repositories` share native account/generation/conversation-bound, expiring, one-use plans. Ten target kinds cover Actions repository/environment/organization; Dependabot repository/organization; Codespaces repository/organization/user; and Agents repository/organization secrets supported by the pinned API. Repository and environment targets require the exact selected repo; account/organization targets forbid it. Organization visibility is explicit. Selected/user access requires exact repository IDs (up to 100 unique IDs, empty means none). Metadata writes/deletes receive the same consequential confirmation. Ordinary request body and extra parameters are rejected; no plaintext or caller-supplied encrypted value/key enters the operation channel. Input routes and access fields match pinned GitHub request schemas.

`GitHubSecrets.tsx` supplies destination/access forms, metadata paging, deletion/access changes, expiry and uncertainty handling. No secret-value input exists in the renderer. After destination approval, shared UI/model execution calls the configured native GTK password-entry provider. Its modal dialog shows account, exact target and access, with explicit Encrypt and save / Cancel. Value entry is masked, copied directly from GTK into opaque native custody, and cleared when the dialog closes. Native cancellation/deadline closes the dialog and discards late replies. Values are nonempty and at most 48 KiB; the widget admits one over-limit character to prevent silently accepting a truncated oversized paste. Pasted multiline input is not deliberately truncated. GTK/OS input buffers are not claimed to be secure locked memory.

The production native transport verifies account/credential identity, obtains a bounded public key at a fixed `api.github.com` secret endpoint, validates the key, requests native entry and encrypts it with libsodium sealed boxes. Opaque Rust plaintext is erased via `sodium_memzero` after sealing/drop. Credentials and account identity are obtained again after entry, before the write. Only encrypted fields go onto HTTPS; no redirects or retries. Only 201/204 confirms a save; returned data is fixed metadata, never an echoed private body. Interrupted or malformed responses are uncertain. Metadata reads and writes validate expected envelope, name/target and status.

The Linux binary now links external system libsodium (observed 1.0.22 / `libsodium.so.26`); no crypto implementation or shared library is vendored. License/provenance is included under `product/licenses/system-libsodium`, and actual loader closure is recorded in the release. References: [GitHub secret encryption](https://docs.github.com/en/rest/guides/encrypting-secrets-for-the-rest-api), [libsodium sealed boxes](https://libsodium.gitbook.io/doc/public-key_cryptography/sealed_boxes), [Actions secret API](https://docs.github.com/en/rest/actions/secrets?apiVersion=2026-03-10). Credential/token administration and Enterprise hosts remain unsupported; secret entry requires the native Linux desktop provider.
