## Measurements and interpretation

New task-2 first-request usage was **4,418 cached / 3,872 uncached input tokens**. Task 1 reported 0 cached / 4,958 uncached. First-request system and prefix identities were identical across both tasks. Historical comparison: the old sample changed system text at character 2336 and reported zero cached tokens for task 2; the previous fixed sample reported 4,424. Different transcripts and generation work prevent an overall latency comparison.

Retained observations, reviewed rather than rerun:

- At 2,000 loaded turns, median Chromium fixture mount work was **1,024.2 → 759.5 ms** and append work **7.4 → 6.2 ms** with containment. Earlier-message loading preserved the anchor within 0.19 px; append followed the latest message; thinking state and loaded-text search survived. These results do not establish bounded memory.
- Request serialization median was **4.408 → 1.515 ms**. Requested allocation calls fell from 46,403.5 to 15; peak extra requested live bytes from 7,592,571 to 2,097,152. Exact serialized bytes were preserved. This measures serialization only.
- Working-set extension plus next-cache construction was **9.831 → 5.788 ms**, with identical future reuse and unchanged allocation counts/peak. Compiler work was excluded; both arms charged the same compiler-output copy.
- Retained custody fixture physical file bytes were **47,327,986 raw → 12,902,533 compressed**, about 72.7% lower. Compression has costs: median verified journal-page reads were approximately **1.73 → 6.71 ms**. New checks confirmed lossless content, logical hashes, retrieval and archive round-trip. Compression reduces growth; it does not stop growth.
